## 1. 项目目标与关键决策

将 Ruffle 做成可在 Leaf 中安装、从 Flash 游戏库直接启动、通过掌机按键完整操作的组件。保留所选 Ruffle 版本的 Flash 兼容能力，重点补齐高效 GPU 渲染、输入、菜单、本地持久存档和生命周期适配。图形 API 是实现选择，以实际帧时间、效果、内存、功耗与稳定性决定，不把 Vulkan 作为功能要求或验收条件。

方案已确认：**以 Leaf Flash 游戏库为主入口，Apps 为辅助；复用已有 leaf-12 运行时的 0.1.2 接入和播放已获用户真机确认。后续保持 Ruffle core 与掌机前端分层。** 深入修改前应取得该版本对应源码与构建信息，补测它的 OpenGL ES／Glow 路线；若满足兼容、性能与稳定性目标，可沿用并完善，无需为使用 Vulkan 而更换后端。其 manifest 标注 GLES2，但包内还有 ES3 着色器线索，真实 context 要求待核。确有缺陷或性能收益时，再评估上游 wgpu 的 GL／Vulkan 路线；已有包的声明不等于真机测试结果。

必须明确的边界：

- 优先验证本地适配的 GPU 后端；若采用当前上游默认 wgpu，才适用其 GLES3／Vulkan 能力要求。不能把上游默认实现的门槛套到所有自定义 OpenGL ES 适配上，也不能只凭 manifest 判断本地包的最低 GLES 版本。
- Pocket 1 只有一个模拟摇杆，混合操作的主方案为“十字键走位＋摇杆鼠标”。不设计依赖第二个摇杆的默认功能。
- “保存到本机”“本地备份进度”和“任意时刻即时存档”是三种不同能力。首版必须可靠保存游戏原生进度；通用即时存档单独预研。上述保存与备份均无需账号、联网或云端服务。
- 兼容目标按 Ruffle 自身能力定义，但上游兼容不等于 Pocket 1 上一定流畅。分别记录上游缺陷、资源缺失、设备性能和移植缺陷。

## 4. 推荐架构和 Leaf 集成

~~~mermaid
flowchart TD
  A[Leaf FLASH 游戏库] --> B[Ruffle content pak / path wrapper]
  B --> C[掌机前端与会话控制器]
  C --> D[Ruffle core / AVM1 / AVM2]
  C --> E[菜单与输入映射 / 虚拟鼠标]
  D --> F[经验证的 GPU 渲染后端与显示 surface]
  D --> G[音频 / 视频 / 字体]

  F --> I[Leaf 所在 Wayland 与设备驱动]
  H --> J[Leaf 提供的数据目录 / 游戏资源]
~~~

### 4.1 包结构与启动契约

当前成功基线采用 `RuffleProbe.pak`，安装于主卡 `Apps/mlp1/RuffleProbe.pak/`，声明内部 `FLASH` 系统，识别 `swf`；core 采用 `type:path` standalone，并明确 `supports_savestate:false`。默认游戏目录固定为 `Roms/flash/`，封面为 `Images/flash/`，`flash` 全小写；内部系统 ID 大写不变。根目录现有可执行 `launch.sh` 提供 Apps 测试入口；正式日常使用从 Flash 游戏库选择 SWF。新菜单实现并完成 Leaf 版本验收前，保持 `supports_menu:false`。具体字段按 CONTENT-1（provides.schema=1）及固定版本的公开规范校验。当前规范不接受 Apps/shared/ 或次卡 pak 的 provides。第三方 provides 不允许 requires_direct_drm，不能把停掉 compositor、独占 DRM 写成普通 pak 的默认启动方式。[公开规范](https://github.com/Utility-Muffin-Research-Kitchen/leaf-contracts/blob/main/docs/content-paks.md)

wrapper 必须正确接收游戏绝对路径，处理中文、空格及引号；最后使用 exec，使 Leaf 监督真实的游戏进程。不得把游戏路径直接拼成可解释的 shell 代码。启动前检查依赖、资源与写入目录，失败时显示可理解的原因并正常返回 Leaf。[接入指南](https://leaf.game/develop/adding-an-emulator/)

### 4.2 数据归属

| 数据 | 拟使用位置／策略 |
| --- | --- |
| 二进制、图标、内置模板、许可证 | pak 目录，允许更新整体替换 |
| 用户配置、自定义模板、游戏身份注册表 | USERDATA_PATH 下的 ruffle 子目录 |
| 游戏进度、备份、恢复事务记录 | SAVES_PATH 下组件专用命名空间，按 game_id 分组 |
| 日志和诊断 | LOGS_PATH 下组件专用目录；限量轮换 |
| 可清理缓存 | 单独目录；与存档分开，删除不影响进度 |

上述路径是需求设计，最终解析必须服从目标 Leaf 导出的目录语义。不得写入 release 管理的 .system/leaf，不得把配置和进度放在会被替换的 pak 内。游戏和 pak 可能位于不同卡，挂载点也可能变化；不把 /mnt/sdcard 等物理前缀作为永久游戏身份。[启动器目录说明](https://github.com/Utility-Muffin-Research-Kitchen/miniloong-launcher-switcher)

### 4.3 构建与依赖

以官方 mlp1-toolchain 为 C／C++ 交叉工具链基线，验证 aarch64 Rust target、链接器、sysroot、pkg-config、动态库和目标 libc。该 SDK 提供 EGL/GLES 等接口，不重新分发设备 Mali blobs；SDK 中存在头文件不能证明机器上的驱动具有相应能力。[工具链说明](https://github.com/Utility-Muffin-Research-Kitchen/mlp1-toolchain)

交付记录应固定：Ruffle tag＋commit、Rust 工具链、Cargo.lock、pak schema、最低 Leaf 版本、toolchain image digest 和依赖功能开关。区分构建机工具与目标机库，避免交叉链接到宿主机 X11、音频或图形库。验证缺失符号、libstdc++／glibc 版本、动态加载器路径和离线启动；按选定 Ruffle 版本核对构建机 Java 等生成依赖。[Ruffle 构建与结构说明](https://github.com/ruffle-rs/ruffle#structure)

## 5. 图形迁移：高效使用 GPU 与后端选择

### 5.1 验证顺序

先验证本地 leaf-12 适配实际采用的 OpenGL ES／Glow 路线、GPU renderer 和效果，以它作为性能基线。若已满足需求，直接优先复用；无需为了 API 名称而换成 Vulkan。本地包的 manifest 声明 GLES2，但二进制存在 GLSL ES 3.00 着色器，不能据此认定它仅需 GLES2 context。选择上游默认 wgpu 时，再验证同一 Wayland 会话中的 GLES3 或 Vulkan。不能从 Leaf 使用 GLES2 推导出设备只支持 GLES2，也不能从 Mali-G52 的规格推导出此固件已提供 Vulkan。Mesa 的上游 GPU 支持表不能代替 Pocket 1 的内核、用户态驱动和 WSI 验证。[Mesa Panfrost／PanVK 说明](https://docs.mesa3d.org/drivers/panfrost.html)

GPU 效率验收应记录：实际 renderer／driver、硬件加速证据、帧时间及长帧、CPU 占用、GPU／共享内存、温度或功耗的可用观测。减少不必要的每帧 CPU/GPU 同步、GPU 读回、重复上传和离屏拷贝；但需先确定其是否用于修复画面或驱动问题，再逐项对照测试。能初始化、能显示、使用某个 API，均不能单独证明高效。

| 关口 | 必须证明的结果 | 失败后处理 |
| --- | --- | --- |
| G0 环境 | 版本、ABI、权限、显示连接信息完整 | 修正运行和构建环境 |
| G1 驱动 | 所选后端要求的 GLES2／GLES3 或 Vulkan 能力通过；记录真实 renderer／adapter，排除静默软件渲染 | 判定驱动／固件依赖，不只修改编译参数 |
| G2 呈现 | 用实际 Wayland surface 创建 context／device，连续 present，旋转方向正确 | 查 WSI、格式、窗口句柄、同步和 surface 配置 |
| G3 Ruffle | 矢量、透明、遮罩、混合、滤镜、BitmapData 读回等分类样例正确 | 区分上游能力、驱动限制与移植错误 |
| G4 生命周期 | 开菜单、返回 Leaf、休眠后重建资源不黑屏、不泄漏 | 完成设备／surface 丢失处理 |
| G5 体验 | 代表游戏性能、内存、音频同步可接受 | 建立逐游戏设置及性能等级 |

若评估 Vulkan 路线，探测必须逐项覆盖：内核驱动和节点权限、同架构 libvulkan、ICD JSON 与实际驱动、实例扩展、Wayland surface／present 支持、队列与交换链、wgpu 所需 features／limits、格式和同步。vulkaninfo 能列出设备，只能算部分通过；这不是采用其他合格后端时的发布前置条件。

GLES 路线必须验证 EGL 平台选择、所选后端要求的 context 版本、扩展与纹理格式、framebuffer、读回和实际 surface。本地适配声明 GLES2，需核对其真实实现；当前上游 wgpu 路线则需要 GLES3 级能力。上游默认实现的显示句柄会参与 wgpu instance 创建，不能把桌面实现当作可直接写任意 framebuffer 的播放器。[实例初始化约束](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/render/wgpu/src/backend.rs#L120)

### 5.2 路线选择规则

1. 本地适配的 OpenGL ES／Glow 路线满足兼容、性能和稳定性：优先复用，修补输入、菜单和本地存档；记录与选定上游版本的功能差异。
2. 已有路线存在缺陷，或需要迁移至当前上游 wgpu：验证 GLES3＋wgpu；能够满足需求即可采用，不要求额外实现 Vulkan。
3. Vulkan 全链路可用且有实际收益：作为可选或默认后端，完成同一套内容和生命周期测试；它不是必须交付的功能。
4. 既有后端与可选路线均不成立：单独评估渲染器改造或系统图形栈升级。滤镜、混合、BitmapData、Stage3D 等效果需重新评估，不能承诺桌面等价。
5. 软件 Vulkan／软件 GL：可用于排错，不能用其初始化成功证明掌机性能通过。浏览器＋WASM 只作为独立备选研究，不作为首版默认依赖。

运行时只在“经此设备验证通过”的后端中自动选择。初始化失败可尝试另一条已验证路线；游戏运行中 device lost 不允许无提示切换并假装运行现场保留。恢复不了时应保存可保存的数据、说明错误，再重启游戏。手动更换后端在菜单标注“重启游戏后生效”。

### 5.3 显示功能

- 默认保持原始宽高比、完整显示舞台；提供适应屏幕、原始比例、自定义缩放。拉伸和裁剪是显式选项。
- 一并处理面板旋转、舞台原点、黑边、裁剪和鼠标命中；区分输出分辨率与内部渲染比例。
- 画质与抗锯齿提供低／中／高或按后端实际能力生成的选项；不显示当前后端无法实现的功能。
- 降低内部渲染比例只能解决部分 GPU 开销，不能承诺解决 ActionScript CPU 瓶颈。禁止通过任意改变 SWF 帧率来伪装性能提升。
- 提供可关闭的 FPS／帧时间诊断；效果准确性和性能分别评估。

## 6. 输入模型与动态切换

### 6.1 统一输入适配层

采用“物理按键／轴 → 设备语义 → 活动方案／修饰层 → 虚拟键盘／鼠标 → Ruffle 事件”。Ruffle 已提供键盘、鼠标、文本和焦点等事件，但现有按钮到 KeyCode 的映射不能替代完整的掌机输入系统。[输入事件定义](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/core/src/events.rs)

所有方案使用 Pocket 1 的实际物理标签。首次开发通过诊断页核对方向、轴、ABXY 和 Menu 语义；不能将某个 SDL 原始编号当成未来 Leaf 虚拟设备的固定接口。L2/R2 只按数字按钮处理。

| 编号 | 输入要求 |
| --- | --- |
| INP-10 | 支持键盘按下／释放、多个键同时按下、鼠标移动／按钮／滚轮、文本输入 |
| INP-11 | 摇杆死区、曲线、滞回可调；映射为键盘时处理对向输入策略 |
| INP-12 | 进入菜单、切换方案、断连、失焦、休眠、重启前释放所有已发送的键与鼠标按钮 |
| INP-13 | 多个物理输入映射同一虚拟键时采用引用计数，避免松开一个输入使另一输入失效 |
| INP-14 | 持久切换方案后，等待新方案将接管的按键释放、有效轴回到校准死区再接管；禁用的故障轴不参与等待；取消旧方案的拖拽锁定、连发和长按计时。临时层按 7.2 处理 |
| INP-15 | 菜单导航层不受游戏自定义映射影响；Menu／Guide 不允许被用户重映射覆盖 |
| INP-16 | 配置显示层级和来源：内置模板 → 用户全局默认 → 每游戏选择与覆盖；运行时应用值可选择保存 |

首版动态切换不需要重启游戏：打开菜单 → 选“按键方案” → 左右预览／进入模板列表 → A 应用 → 返回游戏。应用后短暂显示方案名；每游戏默认记忆最后一次保存的方案。12 组模板全部可用；P1 允许收藏最多 4 组作为快速选择集合。

可选快捷组合键放 P1，默认关闭。启用时检查冲突，并完整消费组合键，避免顺带给游戏发出 Select、攻击或移动动作。不要依赖 Menu 组合实现快捷功能，以免与 Leaf 的 Menu 契约冲突。

### 6.2 内置 12 组模板

表中 ABXY 严格按 A／B／X／Y 顺序。所有模板的 Menu 均为内部菜单；菜单内部统一 A 确认、B 返回。所有模板默认 Start=Enter、Select=Esc；可用菜单内虚拟键盘补充输入。模板只是起点，游戏专用映射优先。

| 模板 | 十字键 | 唯一摇杆 | A／B／X／Y | 肩键与用途 |
| --- | --- | --- | --- | --- |
| 方向键＋Space | 方向键 | 同方向键 | Space／Ctrl／Shift／Z | L1=X，R1=C；传统动作 |
| 方向键＋ZX | 方向键 | 同方向键 | Z／X／C／Space | L1=Shift，R1=Ctrl；平台游戏 |
| WASD＋JKL | WASD | 同 WASD | J／K／L／Space | L1=Q，R1=E；字母键动作 |

| 竞速 | 方向键 | 左右转向；上下不绑定 | Space／N／R／Enter | L1=Z，R1=X；R 可能为重开，用户可改 |
| 鼠标点击 | 方向键 | 鼠标 | 左键／右键／Enter／Space | L1=慢速，R1=快速，L2/R2=滚轮上/下 |

尚未绑定的肩键默认不发任何事件，不能擅自绑定退出、重置或删除。允许一个物理键映射组合键，如 Shift＋Tab，并正确按顺序释放。内置模板不可直接覆盖；修改后生成用户模板或游戏覆盖项。每项都应有当前映射预览与恢复默认。

### 6.3 无触摸的后备操作

即使摇杆漂移或不可用，也能用十字键完成所有菜单操作，并从菜单切到“十字键鼠标”模式完成基本点击。键位编辑按实际物理键捕获，超时／B 取消；不允许映射界面把唯一返回路径锁死。

## 7. 虚拟鼠标、文字输入与坐标

### 7.1 虚拟鼠标

需求包括单击、持续按住、拖动、右键、滚轮和可配置双击。游戏自带指针可选择隐藏宿主指针，避免双指针；未提供指针时使用高对比度宿主指针，大小可调。拖拽锁定必须显示“左键锁定”，再按一次释放；打开菜单、切换方案和退出时强制解除。

建议初始参数：摇杆死区 15%，基本速度以完整舞台约 1.5 秒横穿为起点，慢速倍率 0.25，快速倍率 2.0；允许逐游戏调整。参数必须在真机微调，不能用某个游戏的效果当成通用最佳值。鼠标按真实时间步长计算速度，不能随游戏 FPS 改变。

光标逻辑坐标与画面转换应由同一模块管理。若可视舞台区域起点为 x0/y0、缩放为 sx/sy，则从屏幕位置到未旋转舞台位置的基本关系为 x=(screen_x-x0)/sx、y=(screen_y-y0)/sy；旋转与裁剪还需使用完整逆变换。适配层必须明确 Ruffle 接口接收的坐标域，避免与 core 的 viewport 转换重复执行。

点击前先提交最新鼠标位置；拖拽产生 Down→Move→Up 序列。光标保持在有效区域，黑边不得静默映射为另一个游戏位置。验收中心、四角、边缘、小按钮、缩放和旋转后的命中一致性。Stage 的鼠标锁定或相对移动请求只能在已验证后开放，初版不承诺兼容所有此类游戏。

### 7.2 临时鼠标层（P1）

键盘模板可选择一个空闲肩键作为“按住进入鼠标层”，用于点击标题页／开始按钮；松开后返回原方案。启用前显示被占用的键，并要求用户自行解决冲突。触发肩键本身豁免中立等待且不透传给游戏；进入和退出层时释放被覆盖的旧虚拟动作，其他参与重映射的按键释放后才可产生新动作，防止同一次按住变成意外点击。鼠标层内的 ABXY 语义固定且显示在屏幕上。混合游戏优先选择十字键移动＋摇杆鼠标模板，以支持同时移动和瞄准。

### 7.3 虚拟键盘

P0 提供数字、大小写字母、空格、回车、退格、Esc、Tab 和常用符号，适合名字、密码与游戏菜单。十字键选择，A 输入，B 返回，L1/R1 切换布局。区分字符输入与虚拟按键事件，避免把输入名字错误处理成游戏快捷键。

中文菜单字体是 P0；复杂中文输入法可列 P1，不能因菜单能显示中文就声称所有 SWF 输入框支持中文。外接实体键盘为 P1，并考虑自动布局与热插拔。

## 8. 菜单信息架构与页面行为

### 8.1 设计原则

采用 Leaf 风格的列表和页签，字号适配 4 英寸屏幕；默认单屏 6～7 个主项目，大字号时滚动。屏幕底部持续显示 A 确认、B 返回、左右调整、L1/R1 切页等当前可用动作。主要操作不依赖触摸、悬停、鼠标或颜色区分。

首版选择列表式菜单；此前用户在交互概念稿中选择了列表式。当前 0.1.2 尚无此菜单，本节为后续需求。游戏内菜单优先复用 Leaf 的视觉语法；Catastrophe toolkit 可参考列表、滑块、footer 和键盘。是否通过 Rust FFI 复用，或在掌机前端重实现相同风格，属于实现决策，应评估维护和显示上下文成本。[App UI 指南](https://leaf.game/develop/building-an-app/)

### 8.2 一级菜单（推荐：列表式）

~~~text
Ruffle                         [已暂停]
游戏名称
按键：方向键＋ZX    存档：最近本地保存时间／尚无数据

> 继续游戏
  按键方案            < 方向键＋ZX >
  鼠标与按键设置                     >
  本地存档与备份                     >
  画面与声音                         >
~~~

“按键方案”行的左右键预览候选，A 应用；提示“仅本次／保存为此游戏默认”。B 取消尚未应用的变更。应用前释放旧键，返回时等待物理输入中立。不得只更新界面名称却在后台继续旧映射。

其他方案：分页式，将“控制／进度／画面声音”分为 L1/R1 可切的页签。列表式适合首版，关键入口更容易发现；分页式适合选项扩展后使用。两者底层配置和菜单状态机一致。

~~~text
  创建本地备份
~~~

常规返回 Leaf 自动保存到本机；成功时直接返回，不反复确认。保存失败则保留界面，提供“重试／继续返回（可能丢失未保存的进度）／取消”。重启、恢复、覆盖和删除备份等有损操作才显示具体后果确认；默认焦点放取消。

错误信息必须可操作：“存储卡只读，本地保存失败；上次有效备份仍保留”“缺少资源 levels/01.swf”“当前后端初始化失败，可尝试已验证的另一后端”。详细驱动信息放诊断页。

## 9. 本地游戏进度、备份与存档身份

这里的 SharedObject 是开发术语；本项目使用的是 Flash 的本地存档数据，可理解为游戏写出的关卡、解锁、分数或设置等记录，通常由播放器保存为 .sol 文件。“Shared” 不表示需要云端共享，也不是本项目要求的上传功能。

明确需求：**游戏进度、按键配置和备份全部存放在本机的持久存储目录，断网也能保存与读取；无需账号，不上传存档，不引入云同步服务。** “备份”是在本地额外保留几份历史副本，供误操作或损坏时恢复。游戏自身的在线服务依赖与本地保存是不同问题；存档功能本身不得依赖联网。

菜单只使用“保存到本机”“本地备份”“恢复本地备份”等表达；SharedObject、flush、generation 等保留在技术说明和诊断信息中，普通玩家无需理解这些词。本文技术段落中的“同步”指把内存中的数据写入本机存储，不指同步到云端。

### 9.1 三种保存能力

| 能力 | 保存内容 | 本项目要求 |
| --- | --- | --- |
| 游戏原生存档 | SharedObject／.sol 中由游戏产生的数据 | P0，可靠写入与读取 |
| 进度备份槽 | 一组原生存档及元数据的版本副本 | P0，可恢复；不代表保存当前位置 |
| 运行现场快照 | VM 对象、计时器、随机状态、资源、音视频等完整执行状态 | P2，独立研究；首版不承诺 |

Ruffle v0.7.1 的 Player 可 flush AVM1／AVM2 的 SharedObject，析构也会 flush；但此方法没有向宿主汇总成功与失败。默认磁盘后端采用创建文件后写入，没有在该实现中提供原子替换和 fsync 流程。移植必须增加可观测的持久化保障，不能只依赖析构。[Player 实现](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/core/src/player.rs#L2285)、[磁盘后端](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/frontend-utils/src/backends/storage.rs#L46)

“保存到本机”只能持久化游戏已经放入 SharedObject 的内容，不能强制游戏把普通内存中的当前关卡写成存档。没有原生保存机制、只保存到失效服务器、或上游未实现相关能力的游戏，需要清楚显示限制。完整运行现场快照目前没有可直接作为本方案依赖的通用上游接口，官方仍有相关功能请求。[上游存档请求](https://github.com/ruffle-rs/ruffle/issues/1446)

### 9.2 稳定游戏身份

需求：建立稳定 game_id，不以显示名称、当前 SD 挂载前缀或可变内容 hash 作为唯一进度身份。记录根 SWF、资源包相对路径、内容指纹、原始来源 URL（若有）、资源版本、存档命名空间和迁移别名。

Ruffle 的 SharedObject key 与 movie URL 的 host、路径／localPath 和对象名有关；file URL 使用 localhost，AVM1 与 AVM2 选择 movie URL 的方式也有差异。因此改名、搬目录或改变启动 URL 可能导致旧进度不再被找到。[AVM1 key 实现](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/core/src/avm1/globals/shared_object.rs#L128)、[AVM2 key 实现](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/core/src/avm2/globals/flash/net/shared_object.rs#L50)

具体要求：

- 保留 Ruffle 的 SharedObject key 语义，在其外层增加稳定命名空间；不要将所有 .sol 平铺到一个目录。
- 设计稳定逻辑 movie URL 与实际资源位置的映射；必须验证相对路径、localPath、secure 和多 SWF 共享存档语义，不能简单伪造 origin 解决所有问题。
- 同内容搬家可通过指纹和注册表发现候选旧身份；多份副本或更新版本有歧义时，让用户选择沿用或独立进度。
- 修改封面、显示名、pak 更新不改变进度身份。资源版本变化时先备份，不能假设所有版本存档互通。
- 导入旧 Flash／其他 Ruffle 进度时处理 key 与来源映射，不能仅靠同名文件覆盖；保留原始导入档供回退。

### 9.3 持久化策略

| 时机 | 必须行为 |
| --- | --- |
| 游戏显式 flush | 按接口语义返回真实写入结果；不能在实际写入失败时声称成功 |
| 运行期间 | 建议默认每 10 秒检查／flush，比较字节去重；可调为 5～60 秒并经性能测试确认 |
| 进入菜单 | 请求同步并更新状态，失败不阻止继续查看菜单 |
| 正常退出／重启 | 停止输入和游戏推进，flush，等待持久化确认后完成退场 |
| 可协商的休眠 | 在系统允许的时限内同步；若平台不给回调或立即冻结，不能承诺此刻必能保存 |
| 强制杀进程／断电 | 只能依赖此前已提交的数据；不能声称退出钩子仍会运行 |

存储后端应提供写入账本、错误码和成功提交时间。采用同目录临时文件、完整写入、适合目标文件系统的同步与替换步骤，保留上一有效版本。多 .sol 的备份与恢复采用一致的档案集合／generation manifest；单文件原子替换不等于跨文件事务。目标 Leaf 支持的文件系统（如 FAT32/ext4）及双卡场景必须故障注入验证，不能承诺绝对断电安全。

注意 Ruffle 的存储接口有同步返回值。若引入后台 IO，应设计真实的完成确认或适配接口，不能先返回成功再异步失败。显示“已保存到本机”前确认本轮 flush 没有未处理失败，并确认已提交到约定的持久化层。

### 9.4 备份与恢复

首版建议 3 个自动轮换备份＋5 个手动备份槽。每槽记录时间、game_id、游戏内容版本／hash、Ruffle 版本、所有文件清单与校验、备注；缩略图可选。RTC 时间异常时仍保留递增序号，避免排序和覆盖错误。

手动“创建本地备份”必须先 flush 并确认提交成功，再生成完整档案集合；失败时不显示备份成功、不覆盖有效槽。自动备份默认在正常退出，以及恢复或内容升级前的成功提交节点生成；只有内容变化才推进轮换，重复内容或提交失败不覆盖有效历史。备份集合生成期间暂停游戏推进，保证捕获的是同一个已提交版本。

恢复顺序必须固定：暂停与释放输入 → 同步并备份当前数据 → 销毁旧 Player，等待其 Drop 完成 → 验证并原子恢复档案集合 → 重建 Player。若先覆盖磁盘再销毁旧实例，旧 SharedObject 可能在析构时把恢复档覆盖回去。

恢复失败保持原有效档，并提供回退。正在存档或恢复时禁止重复执行同一操作；防止多进程同时写同一 game_id。备份删除、批量清理须明确范围；“清缓存”不得删除任何进度或用户模板。

## 10. Menu 契约、暂停、休眠与退出

### 10.1 Menu 与版本兼容

优先使用 content pak 的 supports_menu:true，由适配层消费逻辑 Guide／BTN_MODE 打开内部菜单。当前公开规范说明：false 时 Menu tap 请求 SIGTERM；true 时 Menu 松开后合成 Guide 按下／释放；系统还保留长按逃生路径。官方教程与规范的描述存在版本差异，因此必须锁定目标 Leaf 版本，按对应规范验收，并设置确切的最低版本，不能填一个推测版本号。[Menu 规范](https://github.com/Utility-Muffin-Research-Kitchen/leaf-contracts/blob/main/docs/content-paks.md#menu-on-a-content-pak-path-core)

不要把普通 Apps 的 Menu 退出规则直接套在游戏内菜单上；不要假设原始 Menu10 总能被应用读取。内部菜单入口不可重映射，Leaf 的强制退出通道必须保持可用。第三方 path core 不会自动继承 RetroArch 的即时存档或 Game Switcher 能力。

### 10.2 状态机

~~~mermaid
stateDiagram-v2
  [*] --> 启动检查
  启动检查 --> 游戏运行: 初始化完成
  启动检查 --> 错误页: 驱动或资源失败
  游戏运行 --> 暂停菜单: Menu / Guide
  暂停菜单 --> 映射编辑
  映射编辑 --> 暂停菜单
  暂停菜单 --> 存档操作
  存档操作 --> 暂停菜单
  暂停菜单 --> 游戏运行: 继续且输入已中立
  游戏运行 --> 休眠处理: 平台通知
  暂停菜单 --> 休眠处理: 平台通知
  休眠处理 --> 暂停菜单: 唤醒并重建资源
  暂停菜单 --> 退出处理: 返回 Leaf
  游戏运行 --> 退出处理: SIGTERM 请求
  退出处理 --> [*]
~~~

开启菜单时暂停游戏时间推进与声音，保留最后画面。不得把菜单导航、映射编辑和存档操作的按键透传给游戏；进入菜单时仅补发清理旧输入状态所需的释放事件。检查异步网络／资源任务是否需要冻结或排队，避免暂停菜单中游戏状态继续变化。

恢复时重置宿主计时基准，不把菜单或休眠经过的真实时间全部加到下一帧 delta。按需要重建 surface、音频流和输入设备；恢复失败时给出可返回 Leaf 的错误页。

区分暂停、保活的 RAM 休眠、系统结束进程和关机。只有验证了进程及内存保留，才能承诺“休眠后继续同一现场”；关机和重启只能恢复已保存的游戏原生进度，除非未来实现了真正快照。

### 10.3 异常退场

SIGTERM 处理器只置位或发送通知，由正常主循环完成释放输入、flush、持久化确认和退出。不能依赖操作系统默认信号处理触发 Rust Drop，也不能在异步信号处理器中直接运行复杂保存逻辑。

卡死脚本应配置有限执行预算与超时提示，并验证长加载与大脚本场景。主进程失去响应时，Leaf 的强制退出是最终恢复手段；SIGKILL 无法保存。异常启动后显示未正常退出提示，优先读取最后完整 generation，保留损坏档供诊断。

## 11. 音频、视频、字体与资源兼容

| 模块 | 迁移要求 |
| --- | --- |
| 音频设备 | 验证目标音频后端、采样率、声道、缓冲、音量、耳机切换、静音和休眠恢复；设备暂时不可用时允许无声运行或重试 |
| 音频解码 | 保留选定 Ruffle 构建需要的 MP3、AAC、Nellymoser 等相关 feature；精简依赖时记录功能差异 |
| 视频 | 按格式逐项验证 CPU／外部解码路径，离线可用；Vulkan 渲染不等于视频硬解，VPU 适配单独评估 |
| 字体 | 区分 SWF 内嵌字体和设备字体；中文菜单与非内嵌中文游戏提供可分发字体和回退，验证字形、行高和内存 |
| 资源加载 | 支持相对路径、子目录、多个 SWF、图片／声音／XML；处理大小写、URL 编码、中文名与本地文件位置 |
| 网站依赖 | 对 FlashVars、原始 URL、base URL、站点锁定、ExternalInterface、fscommand、网络请求明确配置与限制 |
| 不可离线依赖 | 缺失服务器、登录、在线排行、跨域策略和远端 SharedObject 等单独标记；不能当作本地移植自动解决 |

上游已有音频、软件视频和外部视频后端，但本组件需要选择并验证相应依赖。[音频实现](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/frontend-utils/src/backends/audio.rs)、[core 功能开关](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/core/Cargo.toml)、[软件视频](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/video/software/src/backend.rs)、[外部视频](https://github.com/ruffle-rs/ruffle/blob/v0.7.1/video/external/src/backend.rs)

默认本地离线模式。网络访问、打开外链、文件写入等通过明确策略控制，Navigator 只访问允许的游戏资源与数据范围；防止资源路径越界、压缩包路径穿越和恶意脚本持续占用。需要线上资源的游戏可配置域名许可，网络不可用时不得无限卡住加载页。策略属于迁移功能，不能宣称 Rust 实现意味着无需资源隔离。

推荐首版识别 swf；多资源游戏保持完整目录结构。zip 支持列 P1，解包到受控缓存并保留相对路径，不把提取临时路径作为新的存档身份。只有经过核对才启用 Leaf 的 archive pass-through／extract 能力。

## 12. 配置模型与设置生效方式

每个游戏配置至少包含：schema_version、game_id、资源入口与身份信息、活动 profile_id、按键覆盖、鼠标参数、显示与声音选项、存档策略、资源／网络策略、适用的兼容说明。

| 设置 | 生效时机 | UI 行为 |
| --- | --- | --- |
| 按键方案、映射、鼠标参数 | 运行时 | 应用前释放旧输入，不重启游戏 |
| 音量、指针显示 | 运行时 | 立即预览，可保存游戏默认 |
| 比例／缩放／画质 | 能安全重配时运行时 | 同步更新鼠标坐标；不支持热改时明确标注 |
| 渲染后端、依赖构建能力、部分启动参数 | 重启或组件更新 | 显示生效条件，操作前处理存档 |
| 存档身份、原始 URL、恢复进度 | 重启游戏 | 先备份，完成旧 Player 退场后变更 |

配置写入同样采用版本校验、临时文件与可回退更新。未知版本或损坏配置应退回安全默认，并保留原文件；不能因配置错误导致菜单入口消失。导入模板不得包含可执行 shell 命令。

## 13. 性能、稳定性与兼容性验收

以下是建议的日常版本验收目标，需在 B1／F2 得到测量基线后确认。B0 的分类接入与基本播放已通过用户真机反馈，但这些性能与稳定性指标尚未验收。

| 项目 | 初始验收目标 |
| --- | --- |
| 菜单响应 | 对测试集中正常运行的游戏，收到逻辑 Guide tap／物理 Menu 松开至首个可操作菜单画面 ≤200 ms；导航反馈 ≤100 ms |
| 启动 | 本地小型基准 SWF，从选择到可操作 ≤5 秒；复杂资源包单独记录，不以统一时间误判 |
| 基准内容 | 对选定轻量 30／60 fps 样例达到其设计帧率，报告帧时间分布；重型内容给出性能分级 |
| 输入 | 光标速度不依赖 FPS；每种状态切换均无粘键、误点击；相同虚拟键多来源释放正确 |
| 内存 | 记录 RSS、GPU／共享内存与系统 MemAvailable；先测 compositor 与系统余量，再确定预算和拒载门槛 |
| 稳定性 | 代表样例连续运行 2 小时；100 次菜单／方案切换、20 次可用休眠恢复，无持续增长、崩溃或卡键 |
| 持久化 | 故障注入下保留至少一个有效已提交版本；失败明确显示，正常重启读取一致 |
| 安装升级 | 更新／回滚 pak、游戏改名、卡槽／挂载变化不丢已有进度与用户模板 |

不要承诺所有游戏 60 fps。上游兼容性页面按 AVM 语言和 API 分开统计，实现率不能解释为可玩游戏比例。[Ruffle 兼容性说明](https://ruffle.rs/compatibility)

### 13.1 内容测试矩阵

测试集至少覆盖 AVM1 与 AVM2，每类可复用上游已知测试 SWF，再加入有使用授权的实际游戏；测试报告记录来源和 hash。

| 类型 | 核心检查 |
| --- | --- |
| 纯键盘／WASD／方向键 | 多键同时按、长按、松开、不同键码 |
| 鼠标点击／拖拽／滚轮 | 四角命中、锁定释放、低 FPS 下速度、黑边 |
| 键鼠混合 | 十字键移动同时摇杆瞄准、肩键开火 |
| 文本输入 | 大小写、数字、密码、回车、退格、Tab、字体回退 |
| SharedObject | AVM1/2、多个对象、多个 SWF 共享、同名对象隔离、显式／隐式 flush |
| 图形特征 | 矢量、遮罩、blend、filter、BitmapData、Stage3D（以所选上游版本能力为基线） |
| 音视频 | 目标格式解码、长时间同步、暂停和唤醒 |
| 资源依赖 | 相对 URL、FlashVars、原始站点、离线缺失文件、网络超时 |

每个样例至少记录三组结果：桌面同版本 Ruffle、Pocket 1 所选后端、Pocket 1 的备用后端（若有）。桌面也失败的标为上游／内容问题；只在设备出现的问题继续区分性能、驱动和前端。

### 13.2 必须通过的边界用例

1. 按住攻击、拖拽或修饰键时开菜单／换模板／休眠，回来后不粘键。
2. 打开菜单的同一次按键不会点击游戏；摇杆不回中时不会误触新方案。
3. 存储满、只读、拔卡、短写或 IO 错误时不显示成功，旧完整档仍可恢复。
4. 恢复备份后确实读到恢复数据，退出时不会被旧 Player 析构覆盖。
5. 游戏改名、封面修改、pak 更新、卡挂载互换后仍找到相同 game_id。
6. 一个资源包多 SWF 共享 SharedObject；两个无关游戏同名 .sol 互不污染。
7. GPU／surface 或音频流丢失后可恢复，或安全显示错误并返回 Leaf。
8. 模板损坏、映射全空、摇杆漂移时，十字键菜单和 Menu 入口仍可用。
9. SIGTERM、强制退出、正常退出、RAM 休眠、关机分别测试，不混用恢复承诺。
10. 中文／空格／特殊字符路径和缺失资源不造成命令注入或无提示崩溃。

## 14. 主要风险与处理决策

| 风险 | 等级 | 处理与发布门槛 |

### 18.4 一次游戏启动具体发生什么

1. 将包放在**主卡** `Apps/mlp1/RuffleProbe.pak/`，SWF 放到 `Roms/flash/`，在 Leaf 重扫游戏库。扫描合并 `provides`，产生 Flash 分类和其核心关联；无须修改 release 管理的 `.system/leaf`。
2. 玩家在 Flash 分类中选 SWF。Leaf 以该文件的绝对路径调用 `emulators/ruffle-probe/launch-game.sh`，并导出运行目录；游戏与 pak 不一定同卡。
3. wrapper 要求恰好一个可读 `.swf` 路径，核对文件位于导出的 `ROMS_PATH/flash`（兼容旧大写目录），设置 `RUFFLE_FLASH_DIR` 为实际根目录。中文、空格与特殊字符作为参数传递，不经 `eval` 执行。
4. wrapper 设置 Wayland 视频、ALSA 音频、字体、私有库路径，以及 `USERDATA_PATH/ruffle-probe` 下独立的 XDG 配置／缓存／数据目录。若 Leaf 提供虚拟输入设备，则映射给 SDL。数据不写入 pak；但这一步本身还不能证明 SharedObject 可靠落盘。
5. 通过 `LD_PRELOAD` 装入 `libruffle_probe.so`，优先复用系统 SDL2，缺失时才用捆绑 SDL2；以 `exec "$BIN" "$SWF" --fullscreen` 替换 shell，让 Leaf 监督播放器。
6. 测试层记录 context 与 GL 信息；首个 swap 返回后约 500 ms 开始检测新的游戏按键。输入转为 SDL_QUIT 请求退出，避免启动键长按和摇杆漂移立即退场。该层会消费游戏操作输入，是测试设施，不是最终输入框架。
7. 日志写到 `LOGS_PATH/ruffle-probe.log`，上一轮为 `.previous`。首帧日志只代表调用返回，画面正确性仍要目视检查；硬件加速效率需另测。

Apps 根入口设置 `RUFFLE_PROBE_APP_MODE=1` 后复用同一 wrapper：没有参数时只播放包内 `res/Leaf-GPU-Probe.swf`，不进入原播放器的文件浏览器；如有游戏参数，仍走同样的 SWF 路径校验。它额外兼容新旧 env.sh 位置并能从 pak 位置推导主卡路径。
