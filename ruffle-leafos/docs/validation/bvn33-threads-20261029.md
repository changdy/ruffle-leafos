卡顿的主要证据是一个 1.005 秒窗口内仅推进 43 帧，出现 181.786 ms 循环、54.393 ms tick 与 126.483 ms render；本窗口位图解码总计 262.306 ms，明显高于正常窗口。它说明同步按需解码会占用主线程的帧预算，不代表解码总时间全部发生在同一帧，也不能仅凭秒级数据认定某个单帧 GPU 完全没有等待。

第二段采样跨越了战斗结束、选人/选图和重新加载。保留原始日志，但**整段不纳入上述稳定战斗表，也不把它的 291 ms 混合循环尖峰当成稳定战斗结果**。第一段也只覆盖有限角色/地图和短时间，不代表全部技能、变身或长时内存边界。

## 实际线程分工

第一段共 16 个线程。以下 CPU 百分比仍以单核满载为 100%，由线程 CPU 时间增量计算；主线程会迁移 CPU，不能用某一个固定核的低占用判断它没有限制帧时间。

| 线程组 | 数量 | 合计 CPU |
| --- | ---: | ---: |
| Flash 主线程 | 1 | 58.793% |
| `tokio-rt-worker` | 4 | 0.000% |
| `cpal_alsa_out` | 1 | 5.172% |
| `threaded-ml`（PulseAudio 客户端） | 1 | 3.414% |
| Mali 后端、清理、工具及编译线程 | 7 | 5.586% |
| 物理菜单观察、系统音量观察 | 2 | 1.586% |

最后两条线程在系统中仍显示播放器名，按当前源码的两个显式 `std::thread::spawn` 归组，未用调用栈逐条验证。0.000% 表示本段 `/proc` CPU tick 精度下未观察到增量，不代表线程从不工作。

**播放器是多线程进程，但普通 Flash 游戏的 AVM、显示树生命周期、GC、按需静态位图解码和 GLES 命令提交仍在主线程串行执行。** `main.rs` 创建 Tokio 多线程 runtime；`AndroidExecutor::spawn` 使用 `async_task::spawn_local`，`leaf.rs` 在主循环执行 TaskPoll、`Player::tick` 和 `Player::render`。四个 Tokio 工作线程没有把战斗逻辑分摊到四核。

AVM2 生命周期包含有顺序约束的 Enter、Construct、Scripts、Exit，以及可重入 goto。当前 GC/显示树和局部 future 不具备任意跨线程共享契约，GL 资源也在当前上下文创建、提交和释放。因此不直接将 tick/render 并行执行，不通过增大线程数、强制绑核或提高调度优先级宣称提速。

进一步的线程收益需要把可独立执行的数据工作移出主线程，例如有容量上限的解码预取队列；首次显示才启动工作并立刻等待结果仍会阻塞。预取还会增加驻留内存，需要验证预测命中率、失效/退出、OOM 和图形上传的所有权。当前数据不足以安全启用通用后台预取，本轮保留现有线程模型。

Tokio runtime 的行为见[官方说明](https://docs.rs/tokio/1.50.0/tokio/attr.main.html)；GPU 负载口径参考 [Rockchip Mali devfreq 实现](https://github.com/rockchip-linux/kernel/blob/develop-5.10/drivers/gpu/arm/bifrost/backend/gpu/mali_kbase_devfreq.c)。运行中设备的实际计数和本仓库固定源码优先于上游最新实现。

## 已实现的解码候选与主机验证

`render/src/utils.rs` 原来从空 Vec 解压所有位图，最后 shrink。新实现用 Lossless 位图尺寸、格式、调色板和行填充计算初始输出容量；JPEG3 alpha 使用已解码 RGB 的像素数。预留最多 4 MiB，以宽整数计算再截断容量，避免异常尺寸在 32 位前端溢出或引发巨大预分配。该上限只限制预留容量，不是解压总大小上限；尺寸不匹配时继续沿用既有解码/补齐行为。没有永久缓存、改变压缩算法或线程数。

从随包死神 398 个资源中的 13,862 个 Lossless 定义抽取 100 个流：最大的 24 个与余下按步长选取的 76 个，共 59,592,144 字节展开数据。独立微基准使用相同 flate2 1.1.9 / zlib-rs 0.6.3，每轮每流解压十次，八轮交替 A/B 和 B/A，包含相同的输出校验和开销。

Windows 主机 release 结果：原路径平均 1,064.557 ms/轮，预留路径 763.768 ms/轮，耗时下降约 28.25%；所有选中流逐字节一致，各轮校验和均为 `13849659170`。主机同时有 ARM64 构建负载，绝对耗时有波动；每一对都观察到候选较快，仍不能把这个数值外推为 Pocket1 解码或游戏 FPS 提升。

渲染库 19 项主机测试通过，包含本次新增三项，覆盖 RGB32/调色板像素、无效索引透明回退、行与调色板容量、错误/空流和尺寸提示不足/过大。极大尺寸的容量封顶另有断言。原有 wgpu 位图所有权三项回归也通过。

最终工作区 ARM64 release 候选构建通过：`--tuning pocket1`、Cortex-A55、opt-level 3、ThinLTO，与现用版采用同一编译策略；SHA-256 为 `1f0b71a98473bf38966444769d731db446bb9e4602f6297daf366a84606d14fb`。ELF 为 AArch64 PIE，最高 GLIBC 需求仍为 2.35。编译使用工作区已有的 0.7.3 版本字段；本次 Git 提交只收录解码、测试入口及相关记录，保留原有升版/游戏修改，不自动发布或安装。
