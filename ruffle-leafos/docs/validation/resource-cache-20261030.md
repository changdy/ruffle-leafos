# Pocket1：有界像素及静态渲染资源缓存验证

采样始于 2026-10-30，正式安装与收尾于 2026-10-31（Asia/Shanghai）。设备为 Miniloong Pocket1 / leafOS 0.13.0、RK3566 / 四核 Cortex-A55 / Mali-G52。本轮完成缓存实现、主机回归、ARM64 构建及 GLES 隔离验证。已完成正式安装、最终数据核验及临时 Apps / 搜索索引清理。

## 结论与尚存问题

默认采用 **8 MiB CPU 已解码像素缓存、16 MiB 闲置静态 GPU 资源估算预算，后台预解码关闭**。确定性三帧动画夹具在预热后的约九秒窗口中，位图重载、形状创建与上传次数从 272 次降为零；死神限定角色的两段 GPU16 样本也未发生位图重载。像素缓存单独启用主要减少解码，GPU 资源保留进一步减少上传和形状重建，但会增加驻留内存及回收计费成本。

这些结果证明减少了重复工作，**不等于游戏整体提速、消除所有长帧或解决 OOM**。本轮拳皇素材优化版在新候选 / GLES 上被内核 OOM 结束；此前日志已触发低内存退让。旧正式播放器的同游戏 / GLES 隔离对照也被 OOM 结束，本轮共新增两次 OOM，已知内存问题仍未解决。这不能证明新实现没有增加任何内存风险，也不能把两次不固定对战直接当作精确回归比较。全角色、多局长时、休眠及完整兼容性验收仍未完成。

## 实现与预算口径

- CPU 缓存按像素缓冲的实际 `Vec.capacity()` 做 LRU，默认 8 MiB，`RUFFLE_BITMAP_CACHE_MIB` 可设为 0–16 MiB，0 关闭保留。压缩素材身份使用弱引用，不因像素缓存阻止电影卸载；退出清理缓存。单个超预算素材继续按需解码，不强行进入缓存。
- 静态资源按最近实际显示帧保留闲置形状句柄，默认 16 MiB，`RUFFLE_STATIC_CACHE_MIB` 可设为 0–32 MiB，0 恢复一帧未使用即回收的策略。活动队列仍使用弱引用，不持有已卸载电影；最多保留 1,024 个闲置条目。不能估算或单个估算超预算的闲置句柄不保留，在途绘制命令继续拥有自己的句柄。
- GPU 预算是形状几何及纹理有效载荷的**保守估算**，不是驱动实际分配或进程总内存上限。同一纹理跨形状共享时可能重复计费；当前帧必需资源、在途命令、驱动元数据及其他 BitmapData / 滤镜 / 游戏数据不属于闲置预算。没有增加固定的 2–4 帧过期时间：是否继续保留由预算和使用次序决定。
- `static_idle_mib/static_idle_shapes` 与 `static_current_mib/static_current_shapes` 分别是日志窗口内各自的最大值，可能来自不同帧，**不能相加**计算某一时刻的驻留量。Mali 页统计与 RSS 也有共享内存口径，不能相加当物理内存总量。
- 启动及此后约每秒读取 `/proc/meminfo`。`MemAvailable <128 MiB` 或计数缺失/无效时，两个可选预算降为零；`MemAvailable >160 MiB` 后恢复配置值，中间保留原状态，避免边界反复清空和填充。CPU 已缓存像素在策略变更时立即清理，GPU 闲置句柄在下一次完整游戏 render 后按零预算回收。后台在途任务不能瞬间撤销，其完成结果须通过新预算，不能重新填满已关闭的缓存。
- 这是一秒级的可选资源退让，不限制当前帧或游戏主动持有的数据，也不保证阻止突发大分配 OOM。暂停期间不为清理强行推进游戏帧。
- `RUFFLE_BITMAP_PREDECODE=1` 才启用单个后台工作线程，最多四个排队/执行中的任务，单任务推测输出最多 1 MiB，限可有界解码的 Lossless 素材。主线程不等待后台结果；来不及时仍按需解码。失败任务去重、预留字节计费、退出及降预算行为均有回归。GPU 上传仍在渲染线程执行。

实现入口：`render/src/bitmap_cache.rs`、`core/src/static_render_resources.rs`、各渲染后端的 `estimated_cache_bytes()`、`sdl2test-rocknix/src/resource_cache.rs` 和 `leaf.rs`。

## 方法与计量限制

从独立配置、按键与 SharedObject 目录启动，显式 GLES。使用相同选人流程进入一护对鸣人、魂/我爱罗援助、空座町场景，再回放五遍相同的有界物理输入序列。AI、动作、随机数、技能首次出现、系统频率和温度没有逐帧锁定，所以只能比较阶段成本及重复工作，不能用 59.x FPS 的差异或单个最慢帧计算游戏加速比。

每段采集约 25 秒。分析排除首个可能跨采样起点的 perf 窗口，只保留未暂停、目标 60 FPS、没有加载事件或暂停/帧率转换的完整窗口；下表各保留 24 窗，约 24.2 秒。资源快照为独立的约 24 秒范围，边界不与 perf 窗口严格一致。

`ms/提交` 是该阶段累计主线程墙钟时间除以画面提交数，包含 CPU 执行和等待，不是 GPU 硬件帧时间。render、shape、decode/upload 等项目存在包含关系，不可简单相加。最长循环是有限样本的最大值；秒级日志不能重建逐帧 P95/P99。缓存命中/淘汰计数跨采样边界时可能包含此前排队或保留的工作，不应拿窗口内排队数直接当命中率分母。

像素缓存 CPU8 命中约 79.14%，战斗窗口未淘汰，主要减少解码，仍有 609 次位图重载。CPU16 命中约 78.54%，窗口淘汰三次，上传等价量为 25.194 MiB，对照 CPU8 的 19.860 MiB；进入窗口时 CPU16 已保留更多导航/加载阶段像素。因此不能用该样本要求调高默认容量。

同候选 GPU0 到 GPU16 A/B，重复位图上传计数从 600 降为零，shape 与 upload 成本均较低；代价是 collect 从约 0.0580 增至 0.1815–0.1857 ms/提交，以及额外驻留内存。GPU32 没有在这组样本证明比 GPU16 更有利，故保留 16 MiB 默认。GPU 资源仍在时不再向像素缓存请求解码，GPU16 组的零像素命中率不代表缓存故障。

预解码组后台工作 46.177 ms，窗口内排队 175 次、已预解码像素命中 189 次、未使用即淘汰 23 次、来不及或失败均为零；这些计数的边界不同，不能将 189/175 当成功率。该组主线程约占单核 62.75%，最长循环 50.147 ms，尚未证明整体收益，因此后台继续默认关闭；不能仅凭此一次样本断言线程竞争是所有差异的原因。

## 拳皇失败记录

`kof-gpu16` 使用上述候选、CPU8/GPU16/GLES。日志先出现 `leaf-cache-pressure active=true pixel_mib=0 static_mib=0`。此后 26 个 perf 窗口的像素保留均为零；第一个窗口还包含清理前的闲置资源峰值，随后 25 个窗口的 `static_idle_mib` 均为零。内核仍记录 `Out of memory: Killed process 28986 (ruffle-candidat)`，其 anon-rss 为 316,992 KiB、file-rss 为 493,760 KiB。清缓存只能减少可选保留量，不能保证释放游戏和驱动的活动分配。原始证据为本轮本地 `kof-gpu16-complete.log` 与 `kernel-kof-after.txt`。

原安装 `1f0b71a9…` 的逐字节副本使用同一拳皇素材版、GLES 和独立数据目录进行对照，同样被内核结束：`Killed process 2526 (ruffle-installe)`，anon-rss 为 303,784 KiB、file-rss 为 503,900 KiB。`kernel-before.txt` 没有 OOM 记录，`kernel-kof-after.txt` 新增候选的一次，`kernel-kof-installed-after.txt` 再新增原安装副本的一次。原始对照日志为 `kof-installed-complete.log`。因此保留“拳皇 GLES 已知 OOM 未解决”的限制，不将本轮标成整体无 OOM，也不从两个非固定样本推导缓存新增回归幅度。
