## 流式截图与内存保护（0.8.3 开发候选）

同日进一步优化截图临时分配，使用独立候选与用户数据目录验证，未替换正式应用。候选 SHA-256：`cc6e1ef239bed8badc0d2e4ee38bcb8301b9b8a5f30c5167d7152be595bc63b5`。generic ARM64 release 构建通过，最高 GLIBC 需求仍为 2.35；137 项前端、3 项 PNG 专项、3 项语言及 15 项发布脚本主机回归通过。PNG 专项使用实际编码模块，覆盖奇数高度翻转、逐像素 RGB 还原、难压缩全屏的有界输出、无效输入及短写后满卡错误传播；文件层另验证编码失败清理、旧封面保持与编码期间出现新封面时拒绝覆盖。

当前路径保留一份裁剪后的 RGBA 读回，反向逐行转换为 RGB，经 32 KiB PNG 流写入目标文件。移除整图压缩数据与外层 PNG `Vec`，不另建完整 RGB 图片；编码/写入失败清理当前临时文件或未完成照片，封面仍在成功编码、同步后才原子替换。

截图请求在游戏重绘前即时刷新现有低内存策略并收缩闲置缓存，重绘后重新计算裁剪；重绘前及 CPU 读回前都要求 `MemAvailable` 至少为读回字节 + 2 MiB 编码器余量 + 32 MiB 系统余量，全屏约 36.64 MiB。无法读取有效计数也拒绝截图。此数值是保守的准入门槛，不会预留内存，也不证明能抵挡游戏、驱动或其他进程的瞬时分配。

### 独立分配测量

在 Pocket1 上运行 ARM64 小程序，分别调用原编码路径与本次实际 `screenshot_png::write_rgb()`，使用相同锁定 PNG 依赖及合成像素。全局分配器计量原始 RGBA 和编码期间同时存活的分配请求大小；输出为计数 sink，排除实际文件 IO、页缓存、游戏重绘和 GL 驱动读回。结果是临时堆容量口径，不等同 RSS 或整个截图流程的物理内存峰值。

| 尺寸与内容 | 原路径峰值 MiB | 新路径峰值 MiB |
| --- | ---: | ---: |
| 960×720 纯色 | 2.984 | 3.015 |
| 960×720 难压缩 RGB 噪点 | 10.498 | 3.015 |
| 960×540 纯色 | 2.324 | 2.356 |
| 960×540 难压缩 RGB 噪点 | 8.706 | 2.356 |

流式路径的编码增量均为 396,382 B，不随内容或高度增长；包含一行 RGB 和压缩器缓冲。纯色旧路径本身压缩数据很小，流式缓冲略增约 32 KiB；主要收益是避免难压缩画面的扩容峰值。原全屏噪点路径若 `realloc` 搬迁还可能同时持有旧块，分配请求的保守瞬时估算为 12.762 MiB；这不是实际测得的物理 RSS。各独立样本调用结束后新增存活分配均为零，不将其扩大为真实游戏长期无泄漏或不再 OOM。

### 隔离实机检查与边界

- GLES 保持比例 960×540、铺满 960×720、原始大小 320×180；实际 Vulkan 初始化日志确认后保存 960×540。九份 PNG 的 CRC、RGB 格式、方向、尺寸、夹具帧中心像素及位图外背景检查通过，没有播放器菜单/光标/FPS 残留；上采样边缘沿用原验证的平滑容差。
- 封面首次保存、默认取消保持原字节、明确确认覆盖均通过。照片目录被文件阻挡时提示失败，旧封面保持；恢复目录后可继续保存。
- 仅在隔离进程预加载测试库，将 `/proc/meminfo` 重定向到测试文件：模拟 16 MiB 可用内存时拒绝截图，照片数量与旧封面字节保持；移除计数文件时同样拒绝。恢复真实计数副本后两种场景都能重新保存，暂停菜单继续操作。没有通过耗尽系统内存制造真实 OOM，也没有给正式程序添加测试绕过开关。
- 同一暂停画面额外连续保存 10 次铺满截图均成功。该段 `VmHWM` 保持 98,420 KiB；RSS 由 96,636 变为 97,460 KiB，匿名 RSS 由 46,760 变为 47,052 KiB。短样本不支持“所有驻留页完全归还”或长期无增长的结论。
- 两后端均正常退出，日志为 `progress_flushed=true`。内核 `oom_kill` 仍为零。临时 TOOL 清单没有 `provides`；入口移出 Apps 后刷新索引，备份数据库并只清理已确认目录不存在的本次测试记录，核验 Apps 与 FTS 均为零，其他应用记录保留。正式应用、配置与存档逐文件哈希保持，未安装候选或发布 Release。
