# 像素缓存维护优化与本地排查

日期：2026-11-07（Asia/Shanghai）。修改前代码 `b6df473`，应用 0.8.6 / Ruffle v0.7.1；目标仍为 Pocket1 / leafOS。本轮按用户要求先做本地分析、优化和验证，未连接掌机、安装或发布。

## 排查结论与本轮改动

检查 CPU 像素缓存、静态图形活动队列、GLES 闲置池、电影库所有权、BitmapData CPU 复制及前端维护/保存调用路径，得到以下范围有限的结论：

- **已优化：低内存清空像素缓存。** `DecodeCache::set_limit(0)` 原来每删一项都扫描 HashMap 寻找最旧条目，全部清空的成本近似平方增长。改为一次 `retain` 遍历，逐项记账并释放缓存引用。预算为零时所有条目都要删除，无需排序；包括零字节条目。HashMap 桶容量保持复用，扫描成本按容量计算，条目上限仍为 1,024。
- **已优化：卸载素材清理。** `maintain()` 原先收集已失效来源的键到 Vec，再逐个查找删除；现在原地保留仍存活的来源，避免临时分配和二次查找。前端通常每秒调用一次维护，截图路径也会调用，不把它描述为每帧均发生的大开销。
- **保留待测：静态图形回收。** `StaticRenderResources::collect_with_budget()` 每次收集闲置资源的临时 Vec；已有主线程计时可观察成本。本轮没有改变它，以免在未测量时增加额外遍历、持久元数据或改变回收语义。
- **保留待复现：电影库生命周期。** 弱键表的值仍持有电影及其符号资源，单看弱键不能证明可及时释放。解除所有权涉及存活实例继续创建符号、Loader、GC 等行为；需重复加载/卸载与实际对象存活证据，不能直接删除库或强制 GC。继续由计划 14 管理。
- **保留待采样：保存与 GPU 同步。** 前端每十秒在主线程序列化/提交原生进度；完整 BitmapData 覆盖已有免旧目标读回，局部覆盖、混合及来源同步仍有必要路径。仅凭静态调用链不能认定它们是本机卡顿根因，本轮未调整保存周期或 GPU 同步。

本次保持默认 8 MiB 像素预算、后台预解码默认关闭、非零预算的 LRU、像素内容和失败处理。缓存引用删除后，调用方持有的 Arc 像素继续有效；排队/执行/待领取后台任务的预留量仍单独计费，迟到结果遵循新预算。没有扩大缓存、改线程数、引入强制 GC 或修改游戏素材。

## 主机微基准

新增 `player/render/examples/cache_maintenance.rs`，直接调用生产 `DecodeCache`，使用不含 GPU/GC 的原创 2×1 RGBA 解码器。分别填充 64、256、1,024 项；每个样本先完成填充，再单独计时降零清空、全部来源卸载后的维护或全部来源存活时的维护。检查保留字节和淘汰计数。像素仅用于隔离缓存维护成本，不模拟真实大纹理释放。

同一 Windows GNU 工具环境、release opt-level 3、LTO=false，分别构建修改前后可执行文件；四对交替 A/B、B/A，每次每种配置 300 轮。正式测量时无本轮编译进程。下表为四次均值的平均，分配次数含 alloc/alloc_zeroed/realloc 请求，不是存活堆、RSS 或驱动分配；计数器本身有开销。

| 操作 | 条目 | 修改前 μs/次 | 修改后 μs/次 | 临时分配请求/次（前 → 后） |
| --- | ---: | ---: | ---: | ---: |
| 低内存降零清空 | 64 | 15.928 | 4.331 | 0 → 0 |
| 低内存降零清空 | 256 | 136.913 | 20.742 | 0 → 0 |
| 低内存降零清空 | 1,024 | 1,646.905 | 95.588 | 0 → 0 |
| 全部来源卸载后的维护 | 64 | 9.105 | 6.612 | 5 → 0 |
| 全部来源卸载后的维护 | 256 | 39.738 | 28.772 | 7 → 0 |
| 全部来源卸载后的维护 | 1,024 | 156.132 | 116.240 | 9 → 0 |
| 全部来源存活时的维护 | 1,024 | 4.809 | 4.691 | 0 → 0 |

1,024 项清空的四次均值范围为原路径 1,601.523–1,706.567 μs、新路径 81.874–129.588 μs。存活来源维护的对应范围为 4.218–5.742 / 4.249–5.424 μs，重叠，不宣称该路径提速。64/256 项存活维护也约在 0.3/1.1 μs，四次结果不支持有实际意义的变化。

以上证明局部清理工作减少，不能据此推导整机 FPS、真实长帧改善或持续内存下降；也没有证明游戏会频繁用满 1,024 项、触发低内存退让或发生素材卸载。

复测时按[工程工具环境](../build-release.md#工具链与首次准备)设置 Windows GNU 主机与 linker，在隔离 Cargo 配置下构建 `-p ruffle_render --example cache_maintenance --release --target x86_64-pc-windows-gnu --locked --offline`；运行例程传入轮数（默认 200，本轮 300）。两份可执行文件、修改前源码和驱动脚本保存在忽略目录 `work/cache-maintenance-20261107/`，八份原始 CSV 和派生 `summary.json` 在 `outputs/cache-maintenance-20261107/`。
