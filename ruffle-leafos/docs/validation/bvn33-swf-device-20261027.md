# 死神 VS 火影 3.3：SWF 优化实机对照

日期：2026-10-27。用户提供新地址并开启 ADB 后，在同一 Pocket1 / LeafOS、同一已安装播放器及 GLES 高画质下，对照原离线版和[四方法脚本优化副本](bvn33-swf-patch-20261027.md)。本轮样本中，实战平均画面提交频率明显提高，最坏循环尖峰没有改善；不能据此宣称全部角色稳定 60 FPS 或打斗卡顿已全部解决。

## 条件和采样边界

- 两版始终使用已安装播放器 `ea1ce243e9ac527fa031a7575836b8c3b2ae45f9666c0d38611ff5c699383291`，本轮没有重编译或替换播放器，不把前轮 Rust 回归称为本轮重跑。
- 原主 SWF 为 `148592ba6fbffc79938660997ff8ae6d38c4f90d962208c46c41626199a9a4f5`，候选为 `55299ca859fd250bc8bf384a82a58f7c4b1ff29da8e8f17f33e596d4dcb5cfd2`；398 个相同外部资源在测试前逐文件核验。
- 以独立 Apps 测试入口启动，显式 GLES、默认高画质，隔离 HOME、配置、按键和原生进度。没有读取正式进度来制造相同场景，也没有更改正式用户设置。
- 练习和单人对 CPU 均选择一护/鸣人、魂/我爱罗援助、空座町。实战使用同一组 64 次按键：`right,a,y,a,b,a,x,a` 重复八次，每次 120 ms 点击后等待 250 ms。输入日志确认释放；它不能使 AI、随机数和动作逐帧一致。
- 顺序为原版练习、候选练习、原版实战一、候选实战一、候选实战二、原版实战二。练习各测约 35 秒；实战第一组约 35 秒，包含部分开场，第二组到达 60 FPS 场景后额外等 12 秒再测约 25 秒。实战窗口仍可能跨换局；只筛选 `paused=false target_fps=60.00`，不把菜单目标 30 FPS 算入。
- 使用 `leaf-perf` 的 `draws / window_ms` 统计实际画面提交频率，以阶段总耗时除以 draws 计算每次均值；Enter 等细分包含于 tick，不能重复相加。最长循环是所选窗口 max 的最大值，不是其总和或逐帧 p99。屏幕 FPS 只用于核对，不作为计量依据。
- 温度观察约 50–53.75°C；离散 CPU 频率为 1.8–1.992 GHz，未锁定温度、频率或系统负载。所有对比均为短时观察，不是确定性重放，也未计算统计置信区间。

最初将两份 SWF 放在 `.userdata/...` 隐藏测试目录，原版停在 `init game data`。当前 SharedObject 实现拒绝点开头的路径段；移至普通 ROM 测试路径后原版正常加载，现象与该限制吻合。该失败会话单独保留，不进入下表，也没有通过进一步修改 SWF 绕过。

两组平均画面提交频率的观察差约 +79% / +82%，对应 tick 均值下降约 74.7% / 76.6%。反向复测方向一致，截图确认候选在实际命中、掉血、分身和连击期间继续运行，非暂停或黑屏产生的高计数；但动作、AI、换局比例不一致，不能把这些观察差称为通用或严格的加速比。

Enter 成本明显下降，与省去重复数字重建、嵌套 goto 的优化方向相符。本轮没有做四项补丁各自开关的单项对照，不能把全部收益精确归因于某一个方法。游戏的战斗与倒计时本就按帧推进，帧推进恢复后，其墙钟速度也会变化；没有修改相应的帧数、伤害或停顿公式。

长帧仍然存在，且这组候选的最大值比原版短样本更大，不能声称尖峰已减少。128/133 ms 两个窗口的最大 render 约 122/126 ms，窗口位图解码合计约 116/121 ms；204 ms 窗口的最大 tick/render 分别约 79/124 ms、位图解码合计约 144 ms。各值是窗口聚合，不能精确还原到同一帧，但显示剩余尖峰窗口仍有显著素材解码与绘制成本。后续可继续定位动态截图、滤镜及素材重载路径；本轮没有为此更改缓存策略或削减特效。
