# 拳皇 GLES：滤镜临时纹理池增长定位与有界回收

日期：2026-10-31（Asia/Shanghai）。设备为 Miniloong Pocket1 / leafOS 0.13.0、RK3566 / Cortex-A55 / Mali-G52，960×720、GLES。本文记录在[前轮资源缓存验证](resource-cache-20261030.md)之后，针对拳皇 GLES OOM 进一步定位和修复的证据。正式 Flash / Apps 入口与保存退出、861 个安装文件、原用户数据及游戏文件、临时入口与搜索索引清理均已核验；未发布 GitHub Release。

## 当前结论

已定位到 GLES 后端的 **scratch 滤镜临时纹理池没有容量上限**：每次滤镜缓存产生新的尺寸，旧实现创建临时纹理，使用后全部留在池中，只有再次遇到相同尺寸才会复用，直到退出后端才删除。它独立于前轮的 CPU 像素缓存和静态形状缓存，因此即使前两项已因低内存清零，滤镜池仍可能继续占用大量 GPU 内存。

单实例确定性夹具和真实拳皇的 GL 分配记录均支持该机制。正确插桩的旧版拳皇样本中，末次活跃纹理的约 **93.92%** 来自夹具标定的 scratch 创建位置。修复后夹具停止状态的逻辑纹理从 **93.1555 降至 18.0890 MiB**，实际 Mali 分配从 **142.3867 降至 47.4883 MiB**；排除 FPS 叠层后的截图逐像素一致。

本轮还将读回 PBO 闲置池改为有界回收。旧 PBO 池同样没有字节/条目上限，但本轮证据**没有证明它是该次 OOM 的主要来源**。候选通过一段 300 秒插桩资源采样，以及无 GL 预加载的 420 次首局采样和同进程换局后的 240 次采样，均未新增 OOM；其中包含胜利页与选人等阶段，不能称作等长连续战斗。其他角色、背景、技能、多局长时和异常场景仍需验证，不承诺全部 OOM 已解决，也不将不同背景/AI的存活时间或 FPS 当作精确加速比。

## 实现与预算

- scratch 闲置资源同时限制 **16 MiB RGBA 有效载荷、32 个条目**。仍按精确宽高复用，避免改变滤镜坐标与采样范围；超出预算按最近回池次序淘汰最旧资源，并在拥有 GL 上下文的线程显式删除。
- 读回 PBO 闲置资源限制 **8 MiB、16 个条目**。优先复用最小的足够大缓冲，否则复用并扩大最接近所需大小的旧缓冲，减少不同尺寸长期搁置。完成读回后才能回池，不删除尚未完成的读回资源。
- 低内存策略被采样识别后，立即清理这两个后端闲置池，将其预算降至零；压力期间新归还的闲置资源也立即删除。当前操作中的纹理和在途读回继续保持所有权，恢复阈值后重新允许有限保留。内存压力检测仍沿用前轮的约每秒采样及 128/160 MiB 迟滞，不是阻止任意瞬时分配的总内存硬限制。
- 这两项后端池独立于 CPU8 / 静态形状16 MiB 的默认预算。池预算只约束闲置有效载荷，不包含当前滤镜同时使用的资源、显示树主动保留的目标、GL 元数据、驱动布局及在途物理分配，不能当成总 GPU 或进程内存上限。
- 纹理删除会使共享的绑定缓存失效，避免 GL 名字复用后错误跳过实际绑定；新增逻辑分配、创建/删除、池字节与条目、PBO 重分配及 pending 计数。部分 scratch 获取失败时也会归还已取得的资源。

实现入口为 `sdl2test-rocknix/src/idle_pool.rs` 和 `gl_backend.rs`。纯 Rust 池的最低评分选取在评分相同时优先最近回池项；取出使用不计淘汰，禁用和超预算拒收返回对象供调用者删除，字节计算避免 `u64` 累加溢出。

## 内存口径与旧 OOM 证据

`RssAnon` 主要反映匿名常驻页，不能直接等同完整 Rust/AVM 对象大小。此 Mali 驱动的 GPU 分配在 `status` 中大量表现为 `RssFile`，不能将其当成普通可回收文件缓存。前轮 OOM 的候选 file RSS 约 482.19 MiB，Mali 游戏分配约 481.25 MiB；旧正式播放器的 file RSS 约 492.09 MiB，Mali 约 491.87 MiB，二者高度对应。Mali 页与 RSS 有重叠，不能相加当作物理内存总量。

本轮 smaps/rollup 对 `/dev/mali0` 映射报告的 Rss 为零，总和也可能明显低于 status RSS；这是该采集口径无法完整反映驱动页，**不是 GPU 页不占物理内存或已经释放的证明**。应联合 status、Mali context 页数、GL 逻辑分配及内核 OOM 记录判断。

GL 跟踪是请求的逻辑有效载荷，不包含渲染缓冲、布局/对齐、元数据以及驱动延迟释放等全部实际开销；`glDelete*` 被请求后跟踪器即扣除对象，驱动仍可能因在途工作暂时保留物理存储。因此 GL 逻辑量和 Mali 页的差额不能全部归因于某个缓存池。

`base-trace-a` 因启动脚本的 `LD_PRELOAD` 同行替换未匹配，实际上没有加载跟踪库：没有 `glmem-init`，应作为**未插桩基线**，不能引用为 GL 分配计数证据。该进程 PID 28850 随后发生 OOM，记录在较晚的 `filter-base-kernel.txt`；它自身采样结束时的 kernel 快照早于这次 OOM。此前已有的两次 OOM 继续作为前轮历史，不能在本轮新增数中重复计入。

## 单实例确定性夹具

[build_filter_cache_diagnostic.py](../../scripts/build_filter_cache_diagnostic.py) 生成 954 字节 AVM1 / SWF8：30 FPS、48 帧，只有一个 Graphic 实例，带一个 Glow 滤镜；后续帧只改变矩阵尺寸，最后执行 Stop。没有位图定义、BitmapData 脚本或外部资源。设备分辨率及舞台缩放会影响最终缓存像素尺寸，素材定义尺寸不能直接当作设备分配量。

旧基线的 NULL 数据纹理位置 `return_offset=0xefb194 / call_offset=0xefb190` 共调用 138 次，恰为 46 次尺寸对应的三份 scratch；另一个 `call_offset=0xef39b0` 为 46 次目标创建。旧版前者保留 138 份，后者停止时仅剩一个目标。这与源码池行为及候选的独立计数一致，支持将前者标定为 scratch，但不声称偏移本身提供符号名。

| scratch 对象数 | 138 | 12 |

## 正确插桩的旧拳皇基线

`base-traced-b` 为草薙京对八神庵，实际背景 `ice`，共 65 次资源快照。检测到 `MemAvailable <48 MiB` 后主动 SIGTERM，避免继续等待 OOM，正常提交退出。本段不是一次自然结束或证明不会 OOM的运行。
