# 死神 VS 火影 2.6 与 3.3：卡顿原因和 SWF 优化空间

日期：2026-10-28。目标为 Miniloong Pocket1 / LeafOS。本轮对比本地 SWF、反编译脚本和同机隔离实战，复测掌机上已有的 3.3 四方法脚本优化副本；没有生成新游戏补丁或修改播放器。结论是：3.3 的持续慢速主要有重复 UI 构建与 AVM2 时间轴生命周期成本，平均速度改善后仍有素材解码/重载长帧，不能将二者当作同一个问题。

2.6 使用 Normal 单人模式，一护/魂对鸣人/佐助、木叶场景；3.3 两个文件及 LOW 会话均从 Single VS CPU、一护/魂对鸣人/我爱罗、空座町开始。各次采样使用相同的 48 次物理键序列：`right,a,y,a,b,a,x,a` 重复六遍，每键点击约 120 ms 后等待 250 ms。LOW 采样中途返回选图并进入另一地图，援助也发生变化，不能把其合并片段当作同一场景的严格对照。角色版本、地图、AI、招式、预热和换局状态没有逐帧固定，**跨版本不是相同工作负载的严格速度对照**；3.3 对照也不是确定性重放。

每组原采样约 25 秒，仅选择非暂停且目标帧率与该组一致的完整日志窗口。进一步按 loading_finish / select_map / select_finish / loading_start / go_menu_stage 消息检查阶段：前三组所选窗口内没有这些切换；LOW 另剔除选择/加载阶段及跨切换事件的整个窗口，留下两段合计约 18 秒的战斗片段。不能只用目标 30 FPS 区分 LOW 战斗和菜单。窗口仍可能包含局内演出，不能当成全程同一招式。实际 Flash 帧率为 `frames / 窗口秒数`；画面提交频率为 `draws / 窗口秒数`，补帧或额外绘制时两者会不同。阶段均值按总墙钟时间除以 draws，Enter 等细分包含于 tick，不能重复求和。最大循环不含主动 sleep，也不是逐帧 p99。

AVM1 没有计入 AVM2 Enter/Construct/Scripts 的分阶段指标，因此 2.6 的这些日志字段为零不代表不执行脚本。原 3.3 Enter 约占 tick 的 84%，GPU 绘制不是该样本中最大的持续耗时；不能将 Enter 全部解释为纯 ActionScript 字节码或据虚拟机类型断言 AVM1 普遍更快。

优化版平均速度的方向与[前次反向顺序复测](bvn33-swf-device-20261027.md)一致，支持消除 UI 重复工作的方向；没有做四方法单项开关，不能把全部收益归于其中某一个方法。剩余长帧没有因此消失：214 ms 循环所在窗口的最大 render 为 124 ms、位图解码合计 148 ms；另一个 124 ms 循环窗口的最大 render 为 116 ms、解码合计 112 ms。后者与素材处理尖峰吻合，但窗口聚合不能证明所有值来自同一帧，也不能仅凭它锁定某个角色资源或动态截图方法。

采样前后离散 CPU 为 1.608–1.992 GHz、温度约 48–53°C，没有锁定温度/频率。2.6 RSS 观察约 376–417 MiB，3.3 各会话约 586–597 MiB；模式和存活对象不同，不能推导优化的精确内存收益。没有新增内核 OOM/杀进程记录。3.3 原有 #1006 和 MP3 告警保留，完整会话长度不同，不比较告警频率。

## 基于 2.6 的具体差异

### 帧预算与动画调度

2.6 的 30 FPS 预算是约 33.3 ms；3.3 默认战斗逻辑目标 60 FPS，预算约 16.7 ms。3.3 的 `GameConfig.FPS_ANIMATE` 仍是 30，`GameCtrl.checkRenderAnimate` 默认隔一个逻辑帧推进动画；它并非所有角色动画都翻倍，而是更多逻辑/UI 调用叠加更紧的预算。

3.3 `FighterMC.renderAnimate/renderChildren` 手动对主动画和子 MovieClip 调用 nextFrame/goto。当前 Ruffle 的 `frame_lifecycle.rs::run_inner_goto_frame` 会为嵌套 goto 执行整舞台及孤立对象的构建、帧脚本和退出阶段。这解释了为何小控件上的冗余跳帧也可能放大为大量显示树工作。不能直接删掉角色 nextFrame、命中帧或全局生命周期事件来提速。

### 倒计时和气槽的更新方式

| 控件 | 2.6 反编译实现 | 3.3 原版实现 | 已有优化副本 |
| --- | --- | --- | --- |
| 倒计时 | `DefineSprite_1813/frame_1` 每 1,000 ms 更新两个现有数字 MovieClip | `FightTimeUI.render` 每次赋值，`MCNumber.number` 即使数字相同也删旧、建新并 goto | 仅在整数秒数变化时赋值 |
| 气槽 | `DefineSprite_1774/1782` 每 300 ms 更新气条和档位 | `QiBar.InsBar.setProcess` 每次无条件对数字 gotoAndStop | 档位不变时 stop，变化时 goto；保留气量插值和条宽更新 |

以两位倒计时、目标 60 FPS 估算，3.3 原实现可每秒新建约 120 个数字 MovieClip，两个气槽再发起约 120 次数字 goto；这是静态推算，不是本轮逐次调用计数。2.6 避免了如此频繁的 UI 重建，这比笼统归因于“新版特效更多”更具体。已有补丁还减少两处碰撞检测的临时矩形，范围见[四方法补丁记录](bvn33-swf-patch-20261027.md)。

### 素材量和动态位图

2.6 一护外部资源约 1.05 MB、48 个 Sprite、声明时间轴帧合计 3,585；3.3 一护约 1.86 MB、65 个 Sprite、5,121 帧。两者 DefineBitsLossless2 按宽×高×4 累加分别约 65.52 / 88.99 MiB；鸣人约 49.63 / 57.91 MiB。它们是全文件素材展开等价值，**不是同时驻留内存或一次出招解码量**。3.3 主文件反而比 2.6 小，不能只按主 SWF 大小判断运行负载。

2.6 `shadowEffect` 已有 BitmapData.draw 残影，不能将截图开销说成 3.3 独有。3.3 `ShadowEffectView` 同样创建/销毁快照，且重复查询 bounds；`BitmapFilterView → KyoUtils.drawBitmapFilter` 在更新时分配源和滤镜结果两份 BitmapData，draw/applyFilter 后销毁源。动态截图值得单独追踪，但本次性能日志不能把所有解码尖峰归到这些方法。

## 还能怎样优化 SWF

1. **保留并使用已有四方法优化副本。** 本轮复测确认它改善持续慢速；重复制作相同补丁没有意义。设备上原离线版与脚本优化版都存在，需从游戏列表选择 `死神VS火影3.3-脚本优化版`。
2. **下一步优先评估外部角色/特效 SWF 的透明边裁剪。** 本轮只读解码一护、鸣人和 effect.swf，发现以下具体空间。先保护导出/非形状引用、平铺填充和分数 twip 补偿路径，再对剩余项做裁剪和填充矩阵补偿；必须继续保留原文件、字节码、时间轴、碰撞几何及像素对照。

| 3.3 资源 | Lossless2 展开等价值 | 全零外边理论空间 | 按现有形状/引用规则初筛的空间 |
| --- | ---: | ---: | ---: |
| 一护 `ichigo.swf` | 88.99 MiB | 48.22 MiB | 744 张，42.85 MiB |
| 鸣人 `naruto.swf` | 57.91 MiB | 29.86 MiB | 639 张，26.04 MiB |
| `effect.swf` | 88.60 MiB | 22.57 MiB | 308 张，22.21 MiB |

三份资源合计初筛约 **91.09 MiB**，约占其 Lossless2 展开像素量的 **38.7%**；这不是已获得的 RSS 降幅或 FPS 收益，也不是已完成 AVM2 安全验证的可交付补丁。相同尺寸/格式/完整像素的重复定义分别有 58 / 36 / 0 处，去重还需检查引用，不与裁剪数字简单相加。2.6 的一护/鸣人同样有约 57% / 60% 的全零外边，透明边并非新版独有缺陷。

当前仓库 `optimize_swf_bitmaps.py` 明确仅支持 AVM1，**不能直接用于这些 AVM2 资源**。本轮调用它的解析、解码和形状读取函数做只读统计，没有去掉 AVM2 保护开关或输出修改过的资源。实施前应扩展适用边界、核查 AVM2 的导出位图和尺寸访问，再做像素/结构验证及实机长帧对照；即使裁掉透明边，zlib 解码时间也不会必然同比下降。

3. **动态截图复用是另一个候选。** 优先复用一次截图中重复计算的 bounds，再考虑有字节上限、按尺寸复用的缓冲；只有完全退场的残影可回池，仍可见的快照必须独立，复用前清空像素并处理尺寸/滤镜变化。普通 EffectView 和 EffectManager 已有缓存/对象池，不宜重复增加全量预热或无限缓存。
4. **AI/目标列表可减少短命分配。** `getTargetDistance` 的部分调用只需 x，可改标量；`FighterMain.getTargets` 的中间 Vector/concat 可评估按原顺序一次填充。碰撞闭包可延迟到确实需要时创建。这些尚未实施、没有单项耗时证据；在平均 tick 已约 7 ms 时，不应预期仅靠它们解决 100–300 ms 素材尖峰。

3.3 游戏内 **OPTION → QUALITY → LOW → APPLY** 会调用 `setGameFps(30)`，同步设置 `SPEED_PLUS_DEFAULT = 30 / FPS_GAME`、动画间隔和部分效果参数。本轮确实进入目标 30 FPS 的实战，过滤选择/加载后平均约 29.94 Flash 帧/秒，仍有约 137 ms 循环。原始混合采样约 29.39 Flash 帧/秒、最大循环 345.575 ms，后者不能当成稳定战斗长帧。LOW 同时改变游戏自己的画质/效果设置；本轮只测了优化副本的 LOW，没有测原离线版 LOW，也没有做全招式时序等价验收。不要只改 SWF 帧头或在播放器外部限 30 来冒充这套内部模式，也不据这组不同地图片段声称 LOW 优于或差于 MEDIUM 的最坏卡顿。
